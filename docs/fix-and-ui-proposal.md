# 一起听音乐：缓存、卡顿与界面优化方案

- 日期：2026-10-24
- 适用项目：`E:\AI工作文件\listen-together`
- 状态：v1.1.1 已实施并完成循环播放修复
- 原则：保留现有播放同步、音乐库、房间权限和主题体系，只改问题相关路径

## 1. 结论

“歌曲一多程序运行不起来”不是单一缓存问题，代码里有四个相互放大的原因：

1. **整个歌单都在同步，而且每首歌都携带最多 16,000 字符歌词。** 网络 JSON 单帧上限只有 64 KiB。实测 20 首、每首约 1,000 字符歌词时，同步包已经约 100 KiB；没有歌词时，约 200 首也会逼近上限。超过上限后，Host 广播会抛异常，新成员也可能在加入时被断开。
2. **网络发送在界面线程里执行。** Host 每 100 ms 刷新一次界面，并同步向所有成员发送快照；任何一个成员网络慢、停止读取，`sendall` 就可能长时间卡住，于是整个窗口、删除按钮和播放控制一起失去响应。
3. **会话音频缓存固定为 30 MiB，满了只报错，不会清理。** 一首较大的 FLAC、WAV，或者当前/下一首加下载中的文件，就可能超过上限。下载失败后，未使用的旧文件还可能继续占着空间。
4. **批量删除是逐首发命令、逐首刷新。** 选中多首后，每一首都会触发一次完整歌单刷新和网络广播；第一首遇到慢成员时，后面的删除根本执行不到，所以看起来像“一键删除不能用”。

因此推荐同时做三组修复：

- 缓存升级为 **1 GiB 默认额度 + 自动腾挪 + 容量预留**；
- 网络发送移出界面线程，改成 **每成员独立发送队列 + 超时隔离**；
- 同步包改为 **歌单元数据分片/增量更新 + 当前歌词单独发送**；
- 删除改为 **一次批量命令、一次刷新**；
- 最后增加“定位当前歌曲”按钮并调整播放模式按钮位置。

只把缓存从 30 MiB 调到 1 GiB 可以作为临时缓解，但不能单独解决大歌单和慢网络导致的卡死。

## 2. 代码定位证据

| 问题 | 现有实现 | 实际后果 |
|---|---|---|
| 同步包上限过小 | `net/protocol.py` 的 `MAX_JSON_FRAME = 64 * 1024` | 歌单变大后，JSON 直接超限 |
| 歌单携带全部歌词 | `domain/models.py` 的 `QueueTrack.to_dict()` 始终输出 `lyrics` 和 `lyrics_lrc` | 少量带歌词歌曲就能超过 64 KiB |
| 每轮都构造完整快照 | `app_controller.py` 的 `_refresh_snapshot()` 每次序列化整张歌单 | 歌单越大，CPU 和内存压力越大 |
| Host 在界面线程广播 | `app_controller.py` 约 1033 行直接调用 `server.broadcast()` | 慢成员会阻塞计时器、按钮和窗口 |
| 广播逐成员同步发送 | `net/server.py` 的 `broadcast()` 在循环中直接 `peer.send()` | 一个成员慢，后面的成员和 Host 一起等 |
| 控制连接无发送超时 | `net/server.py` 约 247 行、`net/client.py` 约 143 行设置 `timeout=None` | 网络异常时可能无限等待 |
| 缓存满额不自动清理 | `transfer/session_cache.py` 的 `_ensure_capacity()` 只抛 `CacheFullError` | 当前/下一首稍大就下载失败 |
| 下载期间完全跳过清理 | `app_controller.py` 的 `_prune_cache()` 在存在 pending 时直接返回 | 旧文件占位，新的下载更容易失败 |
| 批量删除逐首发送 | `ui/main_window.py` 的 `_remove_selected_queue_item()` 循环调用删除 | 一次删除触发多次广播，慢网络下卡死 |
| 删除按钮未校验归属 | 删除按钮只判断“是否有选中项” | 普通成员选中别人的歌时按钮可用，但服务端拒绝，看起来像按钮失效 |
| 歌单变化整表重建 | `ui/main_window.py` 的 `_rebuild_queue()` 每次清空列表 | 歌多时重建慢，滚动位置也会丢失 |

### 2.1 同步包实测

按当前字段结构统计单条 `snapshot` 的 UTF-8 大小：

| 歌单规模 | 每首歌词量 | 同步包大小 |
|---|---:|---:|
| 20 首 | 0 字符 | 约 6 KiB |
| 20 首 | 1,000 字符 | 约 100 KiB，已超限 |
| 20 首 | 4,000 字符 | 约 381 KiB |
| 20 首 | 8,000 字符 | 约 756 KiB |
| 200 首 | 0 字符 | 约 59 KiB |
| 500 首 | 0 字符 | 约 147 KiB |

这说明即使没有歌词，大歌单也会越界；有歌词时，十几首就可能出问题。

## 3. 目标效果

完成后应达到：

1. 500 首歌曲、带歌词的歌单可以正常加入、同步、切换和重新加入房间。
2. 某个成员断网、延迟高或停止读取时，只影响该成员；Host 和其他成员仍能播放、删除、排序。
3. 所有按钮点击在 100 ms 内得到界面反馈，不再等待网络完成。
4. 选中多首歌曲后，一次操作即可删除；Host 可删全部，普通成员只能删自己加入的歌曲，并给出明确提示。
5. 点击“定位当前歌曲”后，共享歌单滚动到正在播放项，不改变播放状态。
6. 播放模式按钮位于音量滑杆右侧，显示“顺序 / 循环 / 随机”。
7. 保持现有主题、毛玻璃效果、歌词、播放同步、库扫描和房间权限逻辑不变。

## 4. 详细方案

### 4.1 会话音频缓存

#### 推荐参数

- 默认上限：**1 GiB**。
- 上一首、当前、下一首和正在传输的文件始终保留；已经下载过的歌曲在空间允许时继续留在缓存中，超过额度再按最久未使用顺序清理。
- 不缓存整个音乐库；本地已有源文件时继续直接使用本地文件。

按一首歌约 4 分钟估算，1 GiB 可容纳：

| 常见格式 | 单曲约占用 | 1 GiB 大约可放 |
|---|---:|---:|
| MP3 128 kbps | 3.8 MB | 约 280 首 |
| MP3 320 kbps | 9.6 MB | 约 110 首 |
| AAC 256 kbps | 7.7 MB | 约 140 首 |
| FLAC 无损 | 25-40 MB | 约 25-40 首 |
| WAV 无损 | 约 40 MB | 约 25 首 |

这里说的是“缓存池最多能放多少”，不是会提前下载整张歌单。程序仍只下载当前播放需要的歌曲和下一首预取；以前听过的歌曲可以在缓存中保留，方便回头重播。

- 离开房间、正常退出、Host 关房时继续清理；异常退出后下次启动继续清理遗留的 `session-*` 和 `.part` 文件。

#### 缓存策略

1. 下载前先“预留空间”，避免当前和预取同时下载时各自判断都成功、最后超限。
2. 空间不足时按以下顺序处理：
   - 删除已结束会话的 `.part` 临时文件；
   - 删除不在保留集合中的旧缓存；
   - 删除最久未访问的非当前缓存；
   - 仍然不足时，才给出中文错误：需要多少空间、当前缓存上限、建议清理或更新缓存设置。
3. 永不删除上一首、当前、下一首、正在传输中的文件。
4. `prune` 不再因为存在下载就整体跳过；只保护对应的下载文件，其他无用文件仍可清理。
5. 下载失败时立即删除自己的 `.part`，并释放预留空间。
6. 检查磁盘剩余空间，至少为系统保留 2 GiB；不要为了缓存把系统盘写满。

#### 传输顺序

- 当前歌曲最高优先级。
- 下一首预取在进入播放器后再启动。
- 限制为最多 1 个当前下载 + 1 个预取下载；当前歌曲变化时，取消或降级已经失效的预取。
- 成功下载并校验 SHA-256 后才替换正式缓存文件。

#### 可选增强

未来可在“外观”之外增加“缓存大小”设置，提供 512 MiB、1 GiB、2 GiB、自动四档。首版建议先固定 1 GiB，减少界面和配置改动。

### 4.2 网络与同步机制

这是本次最关键的稳定性修复。

#### A. 界面线程不再直接写 socket

- Host 为每个成员建立独立的有界发送队列和发送线程。
- 普通成员也使用独立发送线程向 Host 写控制消息。
- 界面线程只负责“提交命令”，立即返回。
- 数据上传/下载继续使用现有后台线程，不进入界面线程。

发送队列分两类：

- **控制命令**：播放、暂停、删除、排序、切歌等，必须可靠发送，不丢。
- **状态快照**：只保留最新一份；旧快照可直接丢弃，避免慢成员积压。

#### B. 慢成员隔离

- 控制 socket 设置发送/接收超时，例如 8 秒。
- 某个成员超时后只断开该成员，并显示“某某网络断开，正在重连”；其他成员不受影响。
- 广播只负责把消息放入每个成员的队列，不再同步等待所有 socket 写完。
- 不再用 `timeout=None` 长时间无限等待。

#### C. 同步包瘦身与分片

- 歌单中的 `QueueTrack` 同步字段不再携带全部歌词，只保留：
  - `queue_id`
  - `track_id`
  - `source_member_id`
  - `added_by`
  - `title`
  - `artist`
  - `duration_ms`
  - `size_bytes`
- 当前歌曲歌词单独发送，按 `track_id` 缓存；切换歌曲时只取当前这一首。
- 房间状态和歌单分开：
  - 轻量状态消息：当前索引、播放锚点、成员、就绪状态、模式，可高频少量发送。
  - 歌单消息：只在 `queue_revision` 变化或新成员加入时发送。
  - 歌单超过安全大小时按固定条数分片，控制器收齐后再更新界面。
- 非当前歌曲不携带歌词；单帧安全上限调整为 2 MiB，并取消每 5 秒重复发送完整歌单，改为轻量心跳。

#### D. 减少无意义刷新

- 只有房间状态或队列版本变化时才构造网络消息。
- 心跳与播放进度不触发整张歌单序列化。
- 批量加歌/删歌只产生一次歌单版本变化和一次刷新。
- 批量加入时，客户端可按小批发送 `queue_add_batch`，Host 收齐后一次广播。

#### E. 加入房间

- “加入房间”的连接和握手移到后台任务，界面显示“正在连接”。
- 8 秒无响应时给出可重试提示，窗口仍可操作。
- 断线重连状态不阻塞按钮。

### 4.3 一键删除

#### 行为

- 保留“一键删除选中歌曲”的交互，不增加二次确认弹窗。
- 选中多首后，只发送一条 `queue_remove_batch` 命令。
- Host 一次处理、一次更新歌单、一次广播。
- 返回结果包含成功数量、无权限数量和不存在数量。

#### 权限

- Host 可删除歌单内任意歌曲。
- 普通成员只能删除自己加入的歌曲。
- 删除按钮状态：
  - 未选中：禁用。
  - 选中内容全部无权删除：禁用，并提示“只能删除自己加入的歌曲”。
  - 混合选择：可点击，只删除有权项，并提示跳过了多少首。
- 点击后按钮立即显示“正在删除…”并暂时禁用，收到结果后恢复；即使某个成员网络慢，界面也不会冻结。

### 4.4 定位当前歌曲

- 在“共享歌单”标题行右侧增加一个图标按钮 `定位播放`，建议使用准星/播放定位图标。
- 点击后把当前播放项滚动到列表中央，并短暂高亮 1 秒。
- 只定位，不切换歌曲、不改变播放状态、不自动选中后误触删除。
- 没有当前歌曲时按钮禁用。
- 歌单因加歌、删歌、换歌重建时，保留用户原来的滚动位置和选择；只有点击定位按钮时才主动跳回当前歌曲。

### 4.5 界面按钮调整

保持现有三栏布局和主题，只调整底部与歌单按钮。

播放器底部推荐布局：

```text
                 [上一首]  [播放/暂停]  [下一首]

          [音量图标] ───────────── [顺序 / 循环 / 随机]
```

共享歌单标题行：

```text
共享歌单                 12 首    [定位播放]
```

具体调整：

- 把当前位于歌单标题行的播放模式按钮移到音量滑杆右侧。
- 模式按钮使用图标 + 短文字，显示当前模式，点击循环切换。
- “定位播放”放在共享歌单标题行，使用图标按钮并带悬停提示。
- 上一首、播放、下一首保持中心对称；播放按钮稍大，其余保持一致尺寸。
- 普通按钮统一高度约 34-36 px，圆角、间距、悬停、按下、禁用和键盘焦点态统一。
- 只有播放器控制、侧栏开关、定位使用图标按钮；有歧义的操作优先“图标 + 文字”。
- 危险操作继续使用现有红色 `Danger` 样式，不与普通按钮混用。
- 不改变主题预设、毛玻璃效果和整体颜色体系。

## 5. 批量音乐库与加歌优化

歌曲多时，除了缓存和同步包，还有两处会放大等待：

1. 扫描新歌曲时，当前实现每首歌单独提交一次 SQLite。建议同一批扫描使用一个事务，批量写入；界面显示“已扫描 X / Y”。
2. “全部加入”时，每算完一首 SHA-256 就立即刷新整张歌单和广播。建议：
   - 后台批量计算；
   - 合并短时间内的完成事件；
   - 每批只刷新一次；
   - 显示 `正在导入 37/500`；
   - 不在界面线程重复重建整张列表。

这只改变执行效率，不改变“重复歌曲拒绝、选中加入、全部加入”等现有功能。

## 7. 兼容性与回滚

- 大歌单同步协议建议升级版本号。新版本之间可以正常互通；旧版本连新 Host 时给出“版本不一致，请所有成员更新到同一版本”的明确提示。
- 不建议让新旧协议混用，因为歌单和歌词消息结构已变化，混用会再次出现同步异常。
- 本地音乐库无需重新导入；主题、窗口尺寸、音量、显示名等设置保留。
- 首次启动新版本会清理旧会话缓存，这是安全且可恢复的。
- 若新版本出现问题，可回退旧版本；旧版本会继续使用原 30 MiB 缓存策略。
- 网络发送改造只影响消息调度，不改变播放时间线和权限规则。

## 8. 验证与验收

### 自动化测试

- 500 首歌曲、带歌词的歌单：构造、加入、同步、切歌、重新加入均通过。
- 500 首歌单同步包低于 2 MiB 单帧上限，且只有当前歌曲携带歌词。
- 模拟一个客户端停止读取：Host `tick()` 延迟保持在 100 ms 量级，其他客户端正常收到消息，慢客户端在超时后单独断开。
- 缓存额度、预留、LRU 清理、超限报错、`.part` 清理均有单元测试。
- 100 首批量删除只产生一次歌单版本变化；Host 全删、成员删自己、无权删除三种情况正确。
- 定位按钮能把当前歌曲滚到可视区域中央，且不改变播放状态。
- 原有 48 项测试全部通过。

### 手动验收

- 两台或三台电脑通过 Radmin VPN 同时运行。
- 一首成员网络很差时，Host 和其他成员的播放/暂停/删除/排序保持正常。
- 500 首歌单连续播放、拖动排序、批量删除后，窗口无明显卡顿。
- 大型 FLAC/WAV 可缓存播放或给出明确容量提示。
- 切换全部主题后，新按钮文字、图标、禁用态均正常显示。

## 9. 实施顺序

### 第一阶段：稳定性

1. 网络发送线程和慢成员隔离。
2. 同步包瘦身、分片和批量刷新。
3. 缓存 1 GiB、预留和自动腾挪。
4. 批量删除与删除权限提示。

### 第二阶段：界面

1. 增加定位当前歌曲。
2. 播放模式按钮移到音量滑杆右侧。
3. 统一按钮尺寸、间距、图标和状态。
4. 保留滚动位置与选择状态。

### 可选快速补丁

如果只想先得到一个临时版本，可先做：

- 缓存调到 1 GiB；
- 网络发送加超时；
- 单帧上限临时调大；
- 批量删除只刷新一次。

它能缓解问题，但无法长期保证 500 首歌单和慢网络下稳定，因此不建议作为最终方案。

## 10. 已确认结论

- 缓存默认 1 GiB，离房自动清空，本次不增加缓存设置界面。
- “改变歌单顺序”按“顺序 / 循环 / 随机”播放模式处理，按钮已移到音量滑杆右侧。
